# ADR-004 — On-chain registry: LEZ program (not zone SDK)

**Status:** Accepted, 2026-05-22
**Context for:** the brief's "On-chain registry" criterion, which explicitly asks the submitter to choose one of two paths and justify the choice.

> **From LP-0017 §Functionality:**
> *"On-chain registry: the submitter chooses the anchoring approach — either **(a) a LEZ program** or **(b) a direct submission to the consensus layer via the zone SDK** — and provides a brief justification for the choice. Note that decentralised sequencers for zones are not yet shipped: the zone SDK approach requires a single designated actor to perform consensus inscription, which affects the trust model."*

## Decision

We use approach **(a) — a LEZ program** (`methods/guest/src/bin/whistleblower_registry.rs`).

## Why

### 1. The zone SDK path requires a centralised inscriber today

The brief itself flags it: "decentralised sequencers for zones are not yet shipped". The zone SDK path needs a single designated actor to write every anchor record into the consensus layer. That means:

- A trust assumption (the actor doesn't censor anchors).
- A single point of failure (their node down = anchoring stops).
- A coordination burden (every batch-anchor user has to know the actor's endpoint and trust them).

LP-0017 is *whistleblower* infrastructure. Forcing a designated inscriber into the trust model contradicts the brief's "no single point of censorship" goal in the Overview section. A LEZ program runs under whatever LEZ sequencer is live — the same trust assumption every other LEZ user already accepts, no additional party.

### 2. Permissionless write semantics fall out for free

The LEZ program runs as the account owner of the registry PDA, so the `index_batch` instruction's `signer` only needs to be *some* funded LEZ wallet, not a privileged identity. Any third party (an NGO, a journalist collective, an automated guardian) can fund a tiny wallet and run `batch-anchor watch`. With the zone SDK path we'd have to additionally publish the inscriber's authorisation rules, audit them, and document the trust model — work that vanishes when the validator is just the LEZ program itself.

### 3. SPEL-native idempotency

The in-guest `try_insert` skip — see ADR-001 — runs as the same atomic state transition that decrements the user's compute budget. With the zone SDK approach we'd need to push idempotency one layer out into the inscriber, opening up the "what if the inscriber sees the same CID twice from different anchorers and the dedup logic is buggy?" failure mode. A LEZ program's account state IS the dedup ledger by construction.

### 4. SPEL IDL → off-the-shelf tooling

Choosing the LEZ program means the SPEL framework auto-generates the IDL (`idl/whistleblower_registry.json`, regenerated by `make idl`). That IDL is consumed by the `spel` CLI, by `chronicle-style` inspectors, and by anyone wanting to write a third-party indexer — they don't need to learn a custom wire format. The zone SDK path has no equivalent generator: clients would have to hand-write the message serialiser for our specific inscription format.

### 5. Performance is comparable

The brief asks us to document CU cost for single-CID and 50-CID batch (see `docs/BENCHMARKS.md`). The LEZ program path's cost is dominated by Borsh encode/decode of the `Registry` PDA + the per-CID `BTreeMap::insert` (O(log n) per entry). Empirical numbers are pending devnet access; the structural shape — `α + β · entries_total + γ · batch_size` — is well-understood and lands comfortably inside the LEZ per-transaction budget at 50 CIDs.

The zone SDK path would shift cost off-instruction (no proof generation per anchor, just consensus inscription bytes) but trade that for the trust + tooling cost above. Not a worthwhile trade for this use case.

## What we give up

- **Marginally higher per-anchor cost.** Each `index_batch` requires Risc0 proof generation; the zone SDK path skips that. With batches of 50 we amortise the proving cost over many CIDs, so the cost per anchored CID stays bounded — but a single-CID anchor pays a fixed proof-time premium.
- **Account-data cap.** The registry PDA is bounded by SPEL's 100 KiB account-data limit, capping us at ~900 entries (see ADR-001). The zone SDK path is unbounded. A v2 program can shard by content-prefix once we hit the cap; until then 900 entries is a long testing horizon.

## Consequences

- The on-chain registry lives in `methods/guest/`, built via `cargo risczero build`.
- The SPEL IDL at `idl/whistleblower_registry.json` is regenerated on every deploy.
- Off-chain tooling (`batch-anchor` CLI, the FFI cdylib for the Basecamp plugin) speaks to the LEZ sequencer via the SPEL CLI / `lgs` — no custom inscriber RPC.
- The trust model is the same as any other LEZ program: trust the LEZ sequencer's liveness + safety properties, nothing else.
- Should the LEZ team ship decentralised zone sequencers in the future, the off-chain envelope schema (ADR-002) stays unchanged — a v2 implementation could submit the same `(cid, metadata_hash, anchor_timestamp)` tuples via the zone SDK without touching the publisher side.
